
# 9. Architecture Decisions

## ADR-001: Technology Stack for the PacMan System

**Status:** Accepted

**Context:**
The PacMan system lets players play a maze game in the browser,
submit scores, and compete on a leaderboard. It is built as a coding kata
inside the Agentic SDLC course, so the stack must fit the course toolchain
(Python 3.12, React 18, GitHub Actions, pytest and pytest-bdd, Docker),
be simple to run and deploy, and be testable backend-first in later
modules. Game play is real-time, while scores and the leaderboard are
plain request/response.

**Decision:**

| Concern | Decision |
|---------|----------|
| Game loop and rendering | Run client-side in the browser, drawn on an HTML5 Canvas inside a React component |
| Frontend | React 18 single-page application, written in TypeScript, built with Node 20 |
| Backend API | Python 3.12 with FastAPI, REST/JSON over HTTPS |
| Data storage | SQLite (database file on a Docker volume) behind a repository layer |
| Authentication | External OIDC identity provider (Google Sign-In); the API verifies the ID token |
| Testing | pytest and pytest-bdd for the backend, Vitest for frontend game logic, backend first |
| Packaging and CI/CD | Docker image built and tested with GitHub Actions |
| Diagrams | PlantUML with C4-PlantUML, SVGs generated by a pre-commit hook |

**Rationale:**
- Python 3.12, React 18, pytest, pytest-bdd, Docker, and GitHub Actions are the course toolchain, so every later module works without extra setup.
- A 60 FPS game loop needs low latency and cannot depend on network round trips, so it runs in the browser. Only scores and leaderboard requests go to the server.
- FastAPI is lightweight, has built-in request validation, and generates API docs, which helps with backend-first TDD and BDD.
- Vitest runs game-logic unit tests on Node 20 without a browser, keeping the client testable as ADR-002 requires.
- SQLite needs no database server, which keeps local setup, tests, and deployment simple. The repository layer allows a move to PostgreSQL later without changing the API.
- Delegating login to an identity provider avoids storing passwords and keeps the API focused on scores and the leaderboard.
- Keeping diagrams as PlantUML text lets them be versioned and reviewed in Git next to the code.

**Consequences:**
- Scores come from a client the player controls, so the API can only run plausibility checks (e.g. maximum possible score, play time) and cannot fully prevent cheating.
- SQLite supports few concurrent writers, which is acceptable for a kata but would need a switch to PostgreSQL if the system grew.
- The frontend and backend use two languages (TypeScript and Python), so the API contract must be kept explicit and tested.
- The system depends on an external identity provider being available for login.
- Game logic (maze, ghosts, collisions) must be testable on its own in the client, separate from rendering.

## ADR-002: Run the game loop client-side

**Status:** Accepted

**Context:**
The game must render at 60 FPS, about 16.7 ms per frame, with responsive
input. A network round trip in the frame path would add latency and jitter.
ADR-001 already selects a React 18 / TypeScript browser client with an HTML5
Canvas and a Python request/response API. Chapter 1 makes real-time
performance the top quality goal.

**Decision:**
Run the game loop, state updates, collision detection, and Canvas rendering in
the Game Client inside the browser. The Game API handles only score submission
and leaderboard reads.

**Rationale:**
- Keeps input-to-frame latency local and independent of server or network conditions.
- Uses the chosen Canvas stack without adding a real-time transport.
- Leaves the API as simple REST/JSON, which suits backend-first testing.
- Alternatives considered:
  - A server-authoritative loop with state streamed to the browser: rejected because network latency would break the frame budget and would need a transport not in the chosen stack.
  - Polling the API for game state: rejected for the same latency reason and for needless load.
  - Rendering frames on a server and shipping images: rejected as bandwidth-heavy and slow.

**Consequences:**
- Game logic must be written in TypeScript and kept separate from rendering so it can be unit-tested.
- Game state is lost on reload; only submitted scores persist.
- The client controls the score, so server-side verification of play is not practical without server-side simulation.

## ADR-003: Delegate authentication to an OIDC provider

**Status:** Accepted

**Context:**
A player must be identified when submitting a score, but the system must not
store passwords. ADR-001 chooses Google Sign-In as the external OIDC provider,
and Chapter 3 states that only score submission requires login while the
leaderboard is public.

**Decision:**
Delegate all login to Google Sign-In. The API Client obtains an OIDC ID token;
the Auth Verification component in the Game API verifies it before a score is
accepted. There are no local accounts, passwords, or roles.

**Rationale:**
- Avoids password storage, hashing, and reset flows inside the kata.
- Keeps the API focused on scores and leaderboard data.
- Matches the external partner already shown in the C4 context diagram.
- Alternatives considered:
  - Local username/password accounts: rejected because of the security burden and because it contradicts ADR-001.
  - An API-issued token after proxying the login: rejected as unnecessary complexity that still depends on an identity provider.
  - Fully anonymous submissions: rejected because a stable player identity is needed for the leaderboard.

**Consequences:**
- Login availability depends on an external provider.
- The API must check the token signature, issuer, audience, and expiry.
- Only score submission carries a token; leaderboard reads stay anonymous.
- Changing provider would change token verification configuration, not the API contract.

## ADR-004: Store scores in SQLite behind a repository layer

**Status:** Accepted

**Context:**
Scores must survive restarts, tests must run without a database server, and
ADR-001 selects SQLite on a Docker volume. Chapter 8 requires all persistence
access to go through one component.

**Decision:**
Store scores in SQLite and access it only through the Repository component in
the Game API. The database file lives on a Docker volume in local development
and production, and a temporary file in tests.

**Rationale:**
- No database server is needed to run or test the system.
- The repository keeps SQL out of the endpoints and makes tests easy with a temporary database.
- Storage stays swappable without changing the REST contract.
- Alternatives considered:
  - PostgreSQL: rejected for the kata because it adds a server to run and configure; revisit if concurrent writes grow, as noted in ADR-001.
  - A plain JSON file or in-memory store: rejected because it either loses data or scatters persistence logic across endpoints.
  - Direct SQL in the endpoints: rejected because it couples the API to SQLite and complicates tests.

**Consequences:**
- Few concurrent writers are supported; this is acceptable for the kata.
- The Repository interface must stay storage-agnostic.
- Backups are file or volume backups.
- A future database change needs a new Repository implementation and its tests.

## ADR-005: Deploy production as a single Docker VM

**Status:** Accepted

**Context:**
ADR-001 fixes Docker and GitHub Actions but does not choose a production host.
Chapter 2 forbids assuming a cloud provider, and Chapter 7 needs a concrete
target. The kata needs a simple deployment with SQLite on a Docker volume and
two Docker Compose services, `api` and `web`.

**Decision:**
Deploy production on one Linux VM with Docker Compose, using the `api` service
for FastAPI and the `web` service for Caddy, which serves the built SPA and
forwards API calls. Production uses a domain name with TLS and a matching
registered Google origin; development uses localhost.

**Rationale:**
- Keeps local and production mappings almost identical.
- No managed cloud platform or orchestration to learn.
- SQLite stays on a Docker volume as ADR-004 requires.
- Alternatives considered:
  - Managed container platform: rejected for the kata because it adds vendor-specific configuration and questions about SQLite volume behaviour.
  - Split static host and API host: rejected because it adds two deployments, CORS configuration, and a separate API host.

**Consequences:**
- The VM owns OS updates, TLS renewal, and volume backups.
- There is a single point of failure and no automatic scaling.
- Moving to a managed platform later does not change the Chapter 5 container boundaries.
